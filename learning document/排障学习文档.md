## 2. 逐个问题详解

### 2.1 `read_channel_timing's absolute timer expired`

**现象**：核心/汇聚/服务器交换机下发配置时报这个错，下发失败。

**根因**：
netmiko 的 `send_config_set(commands)` 的工作方式是「**先把一整批命令全部写完，再在末尾一次性读回显**」：

```
写 command1
写 command2
写 command3
...（全部写完）
读回显（一次性读，直到 2 秒静默就提前返回）
```

问题在于 eNSP 上某些命令（如 `interface Vlanif`）执行很慢（实测单条可达 150 秒），期间设备**不输出任何内容**。netmiko 的读回显循环遇到「2 秒静默」就以为命令执行完了，提前返回，于是报 `read_channel_timing's absolute timer expired`（读通道的绝对计时器超时）。

**修复**：把批量下发改成**逐条下发**，每条命令单独等待提示符：

```python
def send_config(self, commands: list) -> str:
    if not self.is_connected():
        return ""
    try:
        output = ""
        if not self.connection.check_config_mode():
            output += self.connection.config_mode()
        for cmd in commands:
            # 每条命令都带 read_timeout=300（5分钟），够慢命令跑完
            # cmd_verify=False 跳过回显校验；auto_find_prompt=False 用稳定提示符匹配
            output += self.connection.send_command(
                cmd, read_timeout=300, cmd_verify=False, auto_find_prompt=False
            )
        output += self.connection.exit_config_mode()
        return output
    except Exception as e:
        logger.error(f"配置下发失败: {e}")
        raise  # 关键：重新抛出，让上层正确感知失败
```

**附带修复**：原来 `except` 里是 `return ""`（吞掉异常），会导致上层 `safe_push_config` 误判「下发成功」。改成 `raise` 重新抛出。

---

### 2.2 `Pattern not detected: 'descriptio'`

**现象**：路由器（SSH 连接）下发配置时报 `Pattern not detected: 'descriptio' in output`。

**根因**：
`send_command` 默认 `auto_find_prompt=True`。这个参数的意思是「**先重新探测一次提示符**」——它会额外发一个回车，然后去读提示符。但在**子视图**（如 `interface ...` 里）下，SSH 连接读到的不是干净的提示符，而是**上一条命令的回显**（如 `description xxx` 被截成 `descriptio`），于是它把这个回显当成提示符，后面真正的提示符就永远匹配不上了。

**修复**：加 `auto_find_prompt=False`，让它用登录时保存的**稳定的 `base_prompt`（主机名）**去匹配提示符，不再重新探测。

---

### 2.3 中文 description 回显校验失败

**现象**：Telnet 下华为设备对含中文的 `description` 命令回显会换行，netmiko 默认的逐条回显校验（`cmd_verify=True`）匹配不到，报 `Pattern not detected`。

**修复**：在 `connect()` 里连接成功后设置：

```python
self.connection.global_cmd_verify = False
```

`global_cmd_verify` 是全局开关，设了之后 `send_command` / `send_config_set` / `save_config` 一并跳过回显校验。

---

### 2.4 老交换机 SSH 连不上

**现象**：8 台交换机（S5700/S3700）用 SSH 连接时，认证成功后主动断开。

**根因**：这些交换机跑的是老版本 VRP（V200R001），SSH 服务不兼容现代 SSH 客户端（netmiko 用的 paramiko）。路由器 AR2220 是较新 VRP，SSH 正常。

**修复**：**按角色**切换连接方式，而不是读 Excel 里的 device_type 列：

```python
'device_type': 'huawei' if row[4] == 'router' else 'huawei_telnet',
```

- 路由器 → `huawei`（SSH）
- 交换机 → `huawei_telnet`（Telnet）

`topology_push.py` 和 `topology_verify.py` 两处都做了同样修改。

---

### 2.5 并发下发 5 → 1

**现象**：并发下发时，`interface Vlanif` 等慢命令更容易超时。

**根因**：`ThreadPoolExecutor(max_workers=5)` 让 5 台设备同时往 eNSP 灌配置，抢模拟器资源，慢命令更慢。

**修复**：改成 `max_workers=1`（串行），减轻 eNSP 压力：

```python
with ThreadPoolExecutor(max_workers=1) as executor:
    ...
```

---

### 2.6 验证脚本大量「异常」误报

**现象**：`topology_verify.py` 跑完后，核心/路由器/汇聚/服务器等设备显示 `VLAN:异常`、`路由:异常` 等，但实际配置是正确的。

**根因**：
登录时 netmiko 会自动执行 `screen-length 0 temporary`（关分页），设备回了一句：

```
Info: The configuration takes effect on the current user terminal interface only.
```

这句回显**残留在通道缓冲区里没被读走**。验证脚本用 `device.send_command("display vlan")`（默认 `auto_find_prompt=True`），它先重读提示符，把这句残留的 Info 误当成提示符，于是真正的 show 输出还没读就被当成「读完了」，返回**空字符串**。

验证脚本的判断又是朴素字符串匹配：

```python
checks['vlan_status'] = '已配置' if 'VLAN' in vlan_out else '异常'
```

`'VLAN' in ""` → False → 误报「异常」。

**修复**：show 命令改用 `send_command_timing`（原样读完整输出，不重读提示符、不受残留回显影响）：

```python
vlan_out = device.connection.send_command_timing("display vlan", read_timeout=30)
```

**验证**：修复后重跑，9 台全部正常（VLAN 已配置、路由有路由、ACL 已配置、接口 UP）。

**顺带确认的配置正确性**（用 `send_command_timing` 抓真实回显）：
- 核心：7 个 VLAN（1/10/20/30/40/100/999）、路由表 8 条、ACL 3000 共 5 条规则
- 路由器：路由表 18 条（默认路由→192.168.100.1、直连 10.0.0.0/30、到各网段静态路由）
- 汇聚 .11：VLAN 1/10/20

### 2.7 TripleDES 弃用警告（误报）

**现象**：脚本启动时打印两行：

```
CryptographyDeprecationWarning: TripleDES has been moved to ...
  "cipher": algorithms.TripleDES,
```

**排查**（连上路由器抓真实数据）：

```
本次 SSH 协商出的加密算法：
  客户端 -> 服务器: aes128-cbc
  服务器 -> 客户端: aes128-cbc

display ssh server session:
  VTY 0  2.0  AES  run  password  admin
```

**结论**：**3DES 实际上根本没被用上，真正加密数据的是 AES-128**。那两行警告是 paramiko 在「加载它支持的所有候选加密算法清单」时，顺手引用了一下 3DES 这个老算法，cryptography 库看到「你引用了要淘汰的东西」就打印提醒。属于「候选清单里被点名」，不是「真的被选中加密」。

**处理三档**：
1. 推荐：不用管（实际已在用 AES）。
2. 嫌碍眼：脚本开头加 `warnings.filterwarnings("ignore", ...)` 屏蔽。
3. 彻底：在路由器上配置 SSH 只允许 AES 算法（设备端命令，需谨慎）。

## 3. 关键知识点

### 3.1 netmiko 三个发送命令的区别

| 方法 | 行为 | 适用场景 |
|---|---|---|
| `send_command` | 发命令 → 等提示符 → 剥离回显和提示符；默认 `auto_find_prompt=True` 会先重读提示符 | 常规 show 命令（但受残留回显影响） |
| `send_command_timing` | 发命令 → 按超时读输出（**不**主动探测提示符） | 输出不规则、有残留回显、慢命令时更稳 |
| `send_config_set` | 批量写配置命令，末尾一次性读回显 | 配置下发（但慢命令会踩「静默超时」的坑） |

### 3.2 `auto_find_prompt` 与 `base_prompt`

- `base_prompt`：登录时保存的**主机名**（如 `AR1-ChuKou`），是稳定可靠的。
- `auto_find_prompt=True`（默认）：发命令前**重新探测**提示符。在子视图里容易把命令回显误读成提示符 → 报 `Pattern not detected`。
- `auto_find_prompt=False`：直接用稳定的 `base_prompt` 匹配，更可靠。

### 3.3 `cmd_verify` 与 `global_cmd_verify`

- `cmd_verify=True`（默认）：每条命令发出去后，会校验设备是否回显了这条命令。中文 description 换行会导致校验失败。
- `global_cmd_verify = False`：全局关闭回显校验，一处设置全局生效。

### 3.4 `read_timeout` 的作用

读回显时等待设备输出的最长时间。默认 10 秒。eNSP 慢命令（`interface Vlanif` 等）需要调大（如 300 秒），否则读循环提前返回报超时。

### 3.5 SSH vs Telnet

- SSH：加密、安全，但老设备可能不兼容。
- Telnet：明文、不加密，但兼容性好，eNSP 老交换机只能用 Telnet。
- 设备连不上时，先判断是「网络不通」「认证失败」还是「协议不兼容」。

### 3.6 `screen-length 0 temporary` 残留回显

netmiko 登录时会自动执行 `screen-length 0 temporary` 关掉分页，设备会回一句 `Info: ...`。这句残留回显是很多「show 命令返回空」问题的元凶。

## 5. 排查方法论（经验总结）

1. **先定位「现象属于哪一层」**：是连接失败（协议/认证）、下发失败（超时/校验）、还是验证误报（读取时机）。
2. **抓真实回显，别猜**：遇到 show 命令「返回空」或「异常」，直接连上去把原始输出 dump 出来看，是配置真没有，还是读法有问题。本次「异常」误报就是靠抓真实回显才定性的。
3. **区分「真慢」和「被误导」**：`absolute timer expired` 一开始被当成「命令太慢」，其实是「批量读回显遇静默提前返回」。两者都要用超时参数，但机制不同。
4. **一次只改一处，改完验证**：本次问题环环相扣，逐条定位、逐条修复、逐条重跑确认。
5. **模拟器 ≠ 真机**：eNSP 慢、并发会抢资源，所以串行 + 长超时是稳妥选择。
6. **善用设备自己的 show 命令做证据**：`display ssh server session`、`display ip routing-table`、`display vlan` 都是验证事实的好工具。

## 7. 附录：手动初始化清单（重建拓扑时参考）

> 核心原则：**手动只做「把设备带起来、让脚本能登录」这一小块；业务配置（VLAN/接口/路由/ACL/NAT）全交给脚本。**
> 脚本能连进设备之前，设备必须有管理 IP、账号、并开启远程登录服务——这些只能 console 手动配。

### 7.1 eNSP 图形界面操作

1. 拖出 9 台设备（1 台 AR2220 路由器 + 8 台交换机）。
2. 按拓扑连线（核心—汇聚—接入—出口）。
3. 点「启动」所有设备。
4. （关键）配一个 **云（Cloud）** 桥接到宿主机，让运行 Python 脚本的电脑能访问到设备的 `192.168.1.x` / `192.168.100.x` 管理地址——没有这一步，脚本永远连不上设备。

### 7.4 ⚠️ 不要手动配的（否则与脚本重复/冲突）

以下脚本会自动下发，手动配了不仅多余，还可能和脚本打架：

- ❌ VLAN 创建（`vlan batch 10 20 ...`）
- ❌ Vlanif 接口 IP（核心 6 个网关）
- ❌ 接口 trunk/access 划分
- ❌ 默认路由 / 静态回程路由
- ❌ ACL 3000、NAT

这些统统写在 `templates/*.j2` 里，脚本渲染后逐台下发。
